# Deploy and scripts (scripts/, patches/)

- Production deploys run only from CI (`.github/workflows/deploy.yml`), in this order, so that everything that can fail without touching production runs first and the only step that changes the live Worker is the last: 1) build and check the Worker (`pnpm run deploy:build`: `deploy:check-env` refuses any `.env*` or `.dev.vars*` file, `opennextjs-cloudflare build`, `deploy:check-maps` refuses `.map` files in `.open-next/assets`, then `scripts/deploy-worker.sh build`), 2) migrate (`MIGRATE_TARGET=prod`), 3) Trigger.dev tasks, 4) ship the Worker (`pnpm run deploy:ship`, which deploys the bundle step 1 built). A failing build, map upload or bundle check stops the deploy before step 2. Migrations must stay backward compatible, because old and new code run side by side. `pnpm run deploy` runs build then ship for a manual deploy.
- `deploy-worker.sh <build|ship> <environment> <release>`. `build`: a wrangler dry run builds the final bundle and its map; with `SENTRY_AUTH_TOKEN` it adds the debug ID (`sentry-cli`), makes ours the only one (`scripts/sentry-debug-id.ts`), checks the map lists our `src/` files, uploads it, then deletes the maps and writes a deploy config (`scripts/worker-deploy-config.ts`). It keeps the verified bundle in `.wrangler-dist` and deploys nothing; a failed build leaves nothing behind. `ship`: checks again that the bundle carries no source map, then runs `wrangler deploy --no-bundle` on exactly that bundle; with no bundle it refuses. Never run `wrangler deploy <file>` by hand: it ignores `wrangler.jsonc` and drops the bindings. `src/lib/deploy-worker.test.ts` and `src/lib/deploy-workflow.test.ts` pin this behaviour and the step order.
- Why the debug ID must be the only one: the bundle holds many Sentry debug IDs (some in lazily loaded modules) and the SDK keeps the last one registered, so `src/lib/sentry-debug-id.ts` replaces both registries the SDK reads (Sentry's `_sentryDebugIds` and Next's own `_debugIds`, which it reads last) with a read only view that holds only our ID.
- Worker frames map back to `src/` through an inline map chain: `pnpm build` runs `scripts/inline-server-maps.ts` (only when `WORKER_SOURCE_MAPS` is set, which `pnpm deploy` does when there is a Sentry token), `next.config.ts` turns on server source maps under the same flag, and `patches/@opennextjs__cloudflare@1.20.16.patch` makes OpenNext write the handler map. When you bump `@opennextjs/cloudflare`, redo the patch (`pnpm patch`) or Worker frames stop resolving to `src/`.
- The chain fails loudly, on purpose: with the flag set, `scripts/inline-server-maps.ts` exits 1 if any map cannot be inlined (a map that does not line up with its chunk, or a chunk that points at a missing map) or no chunk carries one; the build phase of `deploy-worker.sh` refuses to continue when `worker.js.map` lists no `/src/app/` sources (whenever there is a Sentry token) or when `worker.js` still has an inline map. A map reference in a chunk is URL encoded (`%5Bid%5D`), so it is decoded before the file is looked up.
- The Worker runs with Sentry Dedupe off (`workerSentryOptions`) so every route error counts.
- Other scripts: `db-guard.ts` (see root `AGENTS.md`), `r2-cors.ts` (`pnpm r2:cors`), `pr-proof.sh` (publishes PR proof files).
- The pre commit hook runs ESLint and Prettier on staged files only; typecheck and tests stay in CI.
- Every Sentry event carries a `service` tag (`web`, `browser`, `jobs`, set in `src/lib/sentry-options.ts`). Search and alert by `service`, because Sentry replaces the `runtime` tag on job events with the Node runtime.
