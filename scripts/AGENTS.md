# Deploy and scripts (scripts/, patches/)

- Production deploys run only from CI (`.github/workflows/deploy.yml`). The workflow starts from `workflow_run` when the `CI` workflow completes on main, only for a push run with conclusion `success` (a failed, cancelled or pull request run never deploys), and every checkout and Sentry release uses that run's `head_sha` (`DEPLOY_SHA`), the commit CI tested, never the newest main; `workflow_dispatch` stays for a manual run on the ref it was started on. The one at a time rule (`deploy-production`, no cancel) is on the deploy job, not the workflow, so a skipped run never takes the waiting slot. Inside it, before any production write, an automated run deploys only while its commit is still the tip of main (`git ls-remote origin refs/heads/main`), so a rerun of CI for an older commit stops with a notice instead of putting old code over newer; a manual run skips that check, so a rollback stays possible. The `CI` name and its push trigger are pinned by `src/ci-config.test.ts`, the gate by `src/lib/deploy-workflow.test.ts`. The preflight job lists every Worker secret the site needs (`required` in `deploy.yml`, kept equal to the web, usage and email env schemas by `src/lib/deploy-env-list.test.ts`): a missing one skips the deploy before production changes, and the optional `SENTRY_DSN` only warns. The same preflight lists the Trigger.dev Prod env var names through the management API (`GET /api/v1/projects/<ref>/envvars/prod` with `TRIGGER_ACCESS_TOKEN`; the response carries values, so only names are read, through `jq`, and nothing is echoed) and skips the deploy when a name in `trigger_required` (the job, usage and email schemas plus `DEEPGRAM_API_KEY`) is missing or empty; `SENTRY_DSN` only warns there too. Add a new required env name to `env.ts` and to the matching list(s) together. The steps run in this order, so that everything that can fail without touching production runs first and the only step that changes the live Worker is the last: 1) build and check the Worker (`pnpm run deploy:build`: `deploy:check-env` refuses any `.env*` or `.dev.vars*` file, `opennextjs-cloudflare build`, `deploy:check-maps` refuses `.map` files in `.open-next/assets`, then `scripts/deploy-worker.sh build`), 2) migrate (`MIGRATE_TARGET=prod`), 3) Trigger.dev tasks, 4) ship the Worker (`pnpm run deploy:ship`, which deploys the bundle step 1 built). A failing build, map upload or bundle check stops the deploy before step 2. Migrations must stay backward compatible, because old and new code run side by side. `pnpm run deploy` runs build then ship for a manual deploy.
- `deploy-worker.sh <build|ship> <environment> <release>`. `build`: a wrangler dry run builds the final bundle and its map; with `SENTRY_AUTH_TOKEN` it adds the debug ID (`sentry-cli`), makes ours the only one (`scripts/sentry-debug-id.ts`), checks the map lists our `src/` files, uploads it, then deletes the maps and writes a deploy config (`scripts/worker-deploy-config.ts`). It keeps the verified bundle in `.wrangler-dist` and deploys nothing; a failed build leaves nothing behind. `ship`: checks again that the bundle carries no source map, then runs `wrangler deploy --no-bundle` on exactly that bundle; with no bundle it refuses. Never run `wrangler deploy <file>` by hand: it ignores `wrangler.jsonc` and drops the bindings. `src/lib/deploy-worker.test.ts` and `src/lib/deploy-workflow.test.ts` pin this behaviour and the step order.
- Why the debug ID must be the only one: the bundle holds many Sentry debug IDs (some in lazily loaded modules) and the SDK keeps the last one registered, so `src/lib/sentry-debug-id.ts` replaces both registries the SDK reads (Sentry's `_sentryDebugIds` and Next's own `_debugIds`, which it reads last) with a read only view that holds only our ID.
- Worker frames map back to `src/` through an inline map chain: `pnpm build` runs `scripts/inline-server-maps.ts` (only when `WORKER_SOURCE_MAPS` is set, which `pnpm deploy` does when there is a Sentry token), `next.config.ts` turns on server source maps under the same flag, and `patches/@opennextjs__cloudflare@1.20.16.patch` makes OpenNext write the handler map. When you bump `@opennextjs/cloudflare`, redo the patch (`pnpm patch`) or Worker frames stop resolving to `src/`.
- The chain fails loudly, on purpose: with the flag set, `scripts/inline-server-maps.ts` exits 1 if any map cannot be inlined (a map that does not line up with its chunk, or a chunk that points at a missing map) or no chunk carries one; the build phase of `deploy-worker.sh` refuses to continue when `worker.js.map` lists no `/src/app/` sources (whenever there is a Sentry token) or when `worker.js` still has an inline map. A map reference in a chunk is URL encoded (`%5Bid%5D`), so it is decoded before the file is looked up.
- The Worker runs with Sentry Dedupe off (`workerSentryOptions`) so every route error counts.
- `seed-backgrounds.ts` (`pnpm db:seed`, spec 0008): the local run of `ensureBuiltInBackgrounds` (`src/trigger/built-in-backgrounds.ts`; data in `src/lib/built-in-backgrounds.ts`), which uploads each studio from `assets/backgrounds/` (`{slug}.jpg`, 1920x1080, and `{slug}.webp`, 480x270) to `backgrounds/builtin/` in R2 and upserts its `background` row with a fixed ID. Idempotent. It refuses a non local `DATABASE_URL_DIRECT` unless `CI=true` or `MIGRATE_TARGET=prod`. Production and every other environment get the studios from the `cleanup` task (no GitHub secrets: Trigger.dev holds the R2 keys), which skips the `testOnly` placeholder; the deploy workflow installs nothing.
- The built in studios (S3S-T08, spec 0008 AC-7): Toyin's six approved images (`warm-podcast`, `bright-minimal`, `bookshelf-office`, `palette-gradient`, `dark-stage`, `plant-corner`; 1672 by 941 PNG sources in `assets/backgrounds/source/`, which `additionalFiles` does not ship because it copies files only) become `assets/backgrounds/{slug}.jpg` and `{slug}.webp` with the ingest's own ffmpeg graph (`convertArgs` in `src/trigger/ingest-background.ts`: first frame, flattened on black, fitted inside 3840 by 2160 and never enlarged, `-q:v 2`; a 480 by 270 WebP thumbnail, `-quality 85`). To add a studio: put the source PNG there, run those two commands, then add a list entry in `src/lib/built-in-backgrounds.ts` with a new fixed ID (IDs are never reused), a name, plain alt text and the real size; `src/lib/built-in-backgrounds.test.ts` checks the files, sizes and alt text against the list. The warm podcast studio keeps its lit ON AIR sign (Toyin's choice). The placeholder (`testOnly`) is installed only on a local database, never in production.
- Other scripts: `db-guard.ts` (see root `AGENTS.md`), `r2-cors.ts` (`pnpm r2:cors`), `apply-r2-lifecycle.sh` and `.ts` (`pnpm r2:lifecycle`, spec 0013 AC-9: PUTs the rules from `src/lib/storage-lifecycle.ts` to the bucket's lifecycle API with `R2_LIFECYCLE_TOKEN`, a Cloudflare account API token with Workers R2 Storage Edit that only CI deploy holds, never the Worker or Trigger.dev; the `.sh` wrapper prints a `::warning::` and exits 0 when the token is unset, so deploy step 3b never fails for it; PUT replaces the whole rule set, so it is safe to repeat), `pr-proof.sh` (publishes PR proof files).
- The pre commit hook runs ESLint and Prettier on staged files only; typecheck and tests stay in CI.
- Every Sentry event carries a `service` tag (`web`, `browser`, `jobs`, set in `src/lib/sentry-options.ts`). Search and alert by `service`, because Sentry replaces the `runtime` tag on job events with the Node runtime.
