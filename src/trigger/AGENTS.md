# Background jobs (src/trigger)

Trigger.dev v4 tasks, configured in `trigger.config.ts`. Specs: [0001](../../docs/specs/0001-stack-architecture/index.md), [0002](../../docs/specs/0002-data-model/index.md), [0004](../../docs/specs/0004-core-take-loop/index.md).

## What each task owns

- `probe`: ffprobe of the original through a presigned URL, the thumbnail (not fatal), `markUploaded` (this is where media failure codes are set), then it starts and dispatches `process-take`. When the first charge does not fit the monthly allowance (`startJob` says `limit_exceeded`, spec 0014 AC-6) `startAndDispatch` moves the take `uploaded` to `failed` with that code: no job, nothing charged, original and expiry untouched, an info log with the take ID, never a Sentry event. No failed email goes out (the email path is per job); the creator sees it on the take page and the library. Idempotency key `probe-{takeId}` (global scope), so repeated upload completions never probe twice.
- `process-take` file map (RF3-T03, no file past about 250 lines): `process-take.ts` is the task definition, `onFailure`, `failureCodeFor` and `processJob` (the shared part: load the job, `markRunning`, discard earlier renders, download, probe, then the path the kind picks; it removes the temp folder). `take-run/` holds the paths and their shared steps: `full-run.ts` (`fullRun`: waveform, trim, the `background` step, `no_audio` and `no_cuts` endings, render, transcript), `change-run.ts` (`changeRun`: waveform only while the take has none, the `background` step, render, no transcript), `background.ts` (`prepareBackground`: load and download the background, detect the key, the `background` step), `render.ts` (`encode`: render row from the applied cuts, keyed or plain ffmpeg, the final gate and fallback), `ship.ts` (`ship`: upload, `completeLatest`, step, `finish`, email, optional transcript, the task result), `finish.ts` (`finishWithoutRender`; RF3-T07: it acts on the `finish` Result, a refused finish (job cancelled or already final) returns `outcome: "not_finished"` with no email and no transcript), `transcript.ts` (`startTranscript`; RF3-T07: once the transcribe job is started only the dispatch is retried, and if it never goes through the job is finished `trigger_failed`, so no transcribe job is left queued for the stale cleanup), `context.ts` (`RunContext`, `RunResult`, `setStep`). A new path adds its own file and one branch in `processJob`; keep `failureCodeFor` and the task definition in `process-take.ts` (other tasks import it).
- `process-take`: download, local re probe, silence detection (`-35dB`, 700 ms, in `src/lib/trim.ts`), cuts, render, upload, finish. Key `job-{jobId}`. Payloads carry IDs only. Cost guard (HRF-T01): the task has a queue with `concurrencyLimit` `PROCESS_TAKE_LIMITS.perCreatorConcurrency` (2) and every run is triggered with the concurrency key `creator-{id}` (`triggerForJob`, creator looked up by `dispatchJob` and passed as its second argument, `jobTriggerOptions`), so each creator gets their own queue of 2 and one creator's jobs cannot take every slot; a creator's extra jobs wait in the queue.
- Keying guard (S3S-T10): `detectInFile` (`src/trigger/keying.ts`) tries a detected key on the five sampled frames through ffmpeg (`sampleKeyedShare`, same decode and tone map as the render); when the median frame would be more than 85 % transparent the take is `no_green_screen` (`reason: erases_subject`), never an erased person. `preview-background` does the same on its own frame (`io.sampleKeyedShare`) and no longer reuses a latest render key that is too close to neutral.
- `process-take` and backgrounds (spec 0008): a job with `target_background_id` (set by `startJob` from `take.background_id`) has a `background` step. After the trim it loads the background (missing or not `ready` → `BackgroundMissingError` → failure code `background_missing`, refundable), downloads its `image_key`, and `detectInFile` (`src/trigger/keying.ts`) samples 5 frames, tone mapped like the render, and `detectGreenScreen` (`src/lib/keying.ts`) decides. Usable → step `succeeded`, the render keys onto the image (`renderFilterScript(keep, { hdr, hasAudio, background })`, background image as looped input 1, `scale ... out_range=tv` so the output stays limited range). Not usable → step `skipped` with `no_green_screen` and the video keeps its background. Either way a take with a background always renders (AC-2), even with no cuts (the whole take) or no audio (no audio branch in the graph), so the render row records which background it was for; only a take with no background and no cuts skips the render. A ready background whose image is gone from R2 (`R2DownloadError` 404) is `background_missing`. The render row snapshots `background_id`, `background_name`, `keyed`, `key_color`. Final render gate (RF3-T05, spec 0008 AC-13, `src/trigger/render-fallback.ts`): after a keyed `encodeRender` the output's middle frame is compared with the background (`outputIsOnlyBackground`, the preview's `centreDifferenceShare` and `isOnlyBackground`, the background read through the render's own cover chain); only the background means `renderWithFallback` calls `markUnkeyed` (`renders.markUnkeyed`: row `keyed` false, key colour null, name kept, only while `pending`), ends the `background` step `skipped` `no_green_screen`, and renders again without the key into the same file, all before upload, free, no extra email, IDs only in the log. The extra render adds about 2 minutes to a 10 minute take. Detection thresholds and the key settings live in `src/lib/keying.ts` (`DETECTION`, `KEYING`) and were tuned on the synthetic fixtures only: re check them on real footage. Measured on 4 vCPUs (the `large-1x` size): a keyed 10 minute 1080p render takes about 15 minutes against 2 for the plain one (chromakey is the cost, about 20 frames per second); with download, trim and upload a worst case job stays near 20 minutes of the 38.5 minute deadline.
- `process-take` on a background change (spec 0008): a job of kind `background` (`isBackgroundKind(job.kind)`). It downloads the original and probes it, skips the trim and `reanalyse` (the render snapshot comes from `renders.create`, which reads `processing_job.cut_plan` from the job row and applies it over the stored `cut.applied` flags with `effectiveRemovedRanges`, so a change job renders the creator's planned cuts; with no plan the cuts are the same as before; the whole take when there are none). `cut_plan` rule (spec 0011): the task never writes cut flags itself; `finishInTx` applies the plan (`applied` and `creator_changed_at` = the job's `finished_at`) only on success, after checking the new render's `removed_ranges` equal the plan's effective ranges, else it fails the job `render_mismatch` (not refundable, the change job is free) and changes nothing. Cancel and failure apply nothing, runs the `background` step when the job has a target, always renders, charges nothing, queues no email (only `initial` emails) and starts no transcript. A `rerender` of a failed take (take `processing`, started by `startJob`) is still a full run. `tests/background-change-check.ts` runs a change to another studio, a change to a missing image (fails `background_missing`, changes nothing) and back to the original through the real job.
- Late upload rule (spec 0013 AC-7): a take can be deleted while a job runs, so every step that uploads a file checks right after the upload that its take (and job or preview row) still exists, and when it does not it queues its own key in `storage_deletion` (`queueDeletions`, falling back to `deleteObject` first) and requests a drain; the delete itself only queues the keys it can derive. Existing sites: `take-run/ship.ts` (render, `whileJobActive` then `completeLatest`), `preview-background.ts` (`completePreview` says `gone`), `probe.ts` (thumbnail, `markUploaded` not found). A new uploading step copies one of them and adds a test.
- Waveform (spec 0011, AC-11): `process-take` calls `storeWaveform` (`src/trigger/waveform.ts`) right after the local probe, on every non change run and on a `background` job only while `take.waveform` is null (an older take gets one on its first change render), only when the original has audio. One ffmpeg pass (`-vn -ac 1 -ar 8000 -f s16le -`, `runFfmpegBytes`), bucketed by the pure `waveformFromSamples` (`src/lib/waveform.ts`), written through `whileJobActive` + `saveWaveform` (`src/db/data/waveform.ts`). Best effort: a failure logs the take and job IDs and leaves it null; only the job's own deadline is rethrown. Never log the values. It is stored even if the job later fails (the values describe the original, so they stay true).
- `preview-background` (spec 0008, AC-4): payload `{ previewId }`, 2 attempts, 3 minutes (the spec says 2: the shared 90 s deadline margin would leave a 2 minute task only 30 s), queue limit 1 and triggered with the concurrency key `preview-{takeId}` (`triggerPreview` in `src/lib/trigger-runs.ts`), so a take has one preview at a time. `makePreview` loads the rows (`loadPreviewWork`: only a `making` preview with its take and a ready background), presigns the original and probes it over HTTP, seeks to the thumbnail's time (`thumbnailSeconds`, no full download), tone maps, reuses the latest render's `key_color` when it was keyed or runs `detectInFrame` on the frame, composites at 1280 wide with the render's own `compositeFilters` and writes `previews/{takeId}/{previewId}.jpg`. It re reads the rows before it writes and passes its signal to the upload; after the upload a timed out attempt records and cleans up nothing (the retry may own the same derived key). `completePreview` says `gone` (row or take gone, or expired) and the file just written is deleted (queued if that fails), or `superseded` (a retry finished the row) and the file is left alone. No key colour means the plain frame and `no_green_screen` on the row. Final gate (S3S-T12): after the keyed encode `makePreview` reads the still and the background (`io.readImage`, `gateReadArgs`) and, when the centre third barely differs (`isOnlyBackground`), logs the preview, take and background IDs only, encodes the plain frame instead and records `no_green_screen`; never a Ready still of only the background. The seek leaves the keyed frame a little after time 0, which `compositeFilters` now normalises (see `src/lib`). A final failure marks the preview `failed` (`onFailure`). Measured locally: a still in 3 to 4 seconds. `tests/preview-check.ts` runs it for real.
- `notify-take` (`src/trigger/email/`): sends the ready or didn't finish email for one finished job (spec 0006). `process-take` queues it after every `finish` through `queueTakeEmail`, which never throws. 3 attempts; `notified_at` and the Resend key `take-email-{jobId}` make a repeat harmless; a bad email env aborts without retrying. Cancelled jobs send nothing.
- Take emails go through `queueTakeEmail(jobId, kind)`, which queues nothing for a kind that is never emailed (`transcribe`, `rerender` and `background`: only the first run is emailed, spec 0008), and `notifyTakeFinished` refuses such a job too; every caller passes the job's kind (the cleanup sweep gets it from `StaleJob.kind`). Cleanup's stale loop uses a per kind running cutoff.
- In run transcript (spec 0012 task 1): `take-run/transcript-step.ts`, the `transcript` step of `initial` and `rerender` runs, before the render. Works from the run's local `ctx.source` (no presign, no second probe) through the shared `transcript-provider.ts` (Deepgram errors, ffmpeg audio extract, `postAudioFile`; also used by `transcribe-take`). Non fatal: Deepgram failure, a missing `DEEPGRAM_API_KEY` or the 120 s edit deadline (`EDIT_DEADLINE_MS`, `AbortSignal.any` of the run signal and a timeout; bounds ffmpeg and Deepgram only) ends the step `failed` (`provider_rejected`, `timeout`, `provider_error`) and the run goes on. The save uses `whileJobActive` with the run signal only; a cancelled job rethrows (the step is not marked failed). A step this job already ended is reused on a retry (no second Deepgram call). No audio skips it `no_speech`. `ship` and `finishWithoutRender` start the separate transcribe job below only when the step `failed` (`withTranscript` option).
- In run AI cuts (spec 0012 task 2): `take-run/ai-edit-step.ts`, the `ai_edit` step, straight after the transcript step and before the render. One Claude call (`ai-call.ts`: `claude-opus-5-5`, no streaming, SDK `maxRetries: 0`, our own single retry on 429, 5xx and network errors, structured outputs through `output_config.format`, effort `low`; `thinking` is left out because `disabled` is a 400 on this model; token counts are logged, never text) over the words and the rules pause candidates (`src/lib/ai-edit.ts` builds the request with no title, name, email, take ID or URL). `validateAiEdit` drops bad items and refuses the whole answer when word cuts pass 40% of the take or over half the items drop. On success the AI cuts replace the untouched rules cuts through `reanalyse` (`proposedBy` `ai`, kept pauses stored with `applied: false`). Any failure keeps the rules cuts, writes the step `skipped` with reason `ai_unavailable` (or copies `not_english` / `no_speech` from the transcript step) and `ai-unavailable.ts` sends one Sentry message with IDs and the cause only. A missing `ANTHROPIC_API_KEY` (`parseAiEditEnv`) is `no_key`, never an abort. Attempt 2 reuses a final `ai_edit` step (no second call) and the trim step then leaves the stored cuts alone (`aiEditAlreadyFinal`). `writeValid` also stores the validated fixes in `transcript.edits` (`undone: false`) in the same transaction, and the fallback clears them to `[]`; the background suggestion (`take.suggested_background_id` and `suggestion_reason`) is written and cleared in the same transaction (`setTakeSuggestion`). The request carries the built in catalog (`listBuiltInCatalog`: `creator_id` null and `ready`, ID, name and alt only, never an upload); an ID outside it means no suggestion, not a fallback. Never log prompts, answers or reasons.
- `transcribe-take` (spec 0007): started by `process-take` after every successful initial job (rendered, no cuts or no audio; since spec 0012 only when the in run step failed) (`startTranscribeJob`, then `dispatchJob` with `triggerForTranscribe`, key `transcribe-{jobId}`; a throwing trigger finishes the job `trigger_failed`; a refused start only logs). Payload `{ jobId }`; parses `transcriptEnvSchema` itself (`DEEPGRAM_API_KEY`, Trigger.dev env only, a missing key aborts with names only). Presigned original → `probeUrl` → no audio stream skips `no_speech` without calling Deepgram → mono 16 kHz Opus (libopus) in Ogg → plain `fetch` to Deepgram (`src/lib/deepgram.ts`: options incl. `mip_opt_out=true`, zod, `en*` is English) → upsert. 429, 5xx and network retry (3 attempts); other 4xx abort as `provider_rejected`. Skips: `not_english`, `no_speech`, `original_gone`. Final failure codes come from `transcribeFailureCode` (`failTranscribeJob` writes them; the take stays Ready, 0 charged): a 4xx other than 429 is `provider_rejected` (`DeepgramRejected`, status kept on the error), a 5 minute fetch timeout or an attempt past its own deadline is `timeout`, other Deepgram failures `provider_error`. A thrown job start in `process-take` is tried 3 times, then the take shows Make transcript. Never moves the take, charges or emails. Deepgram docs: the `speech-to-text` skill in `.claude/skills/`. Tests inject R2, ffmpeg and Deepgram through `TranscribeIo`.
- `ingest-background` (spec 0008, AC-8 to AC-10): started by `/complete` with `{ backgroundId }`, key `ingest-{id}`, 3 attempts, 5 minutes (`INGEST_BACKGROUND_LIMITS`, deadline wrapper like the others). HEAD the source (more bytes than declared or over 10 MiB: `image_too_large`; missing: `upload_incomplete`), download, `isAnimatedWebp` on the first bytes (ffprobe cannot read an animated WebP), `probeImageFile` (codec, size, packets, and the first frame's rotation from `-show_frames`; the frame is not decoded when the pixel count is over 40 MP), `checkImageFacts` (`image_invalid`, `image_animated`, `image_too_large`, `image_too_small`, the last on the rotated size), then one ffmpeg graph (`convertArgs`): `-noautorotate` plus `rotationFilter` (ffmpeg only auto rotates simple graphs), RGBA flattened on black, fitted inside 3840 by 2160 (never enlarged), `image.jpg` (yuvj420p) and a 480 by 270 cover cropped `thumb.webp`. Files are written, then `saveIngest` re-reads the row under a lock: deleted or already failed, it queues the three keys and writes nothing else. Colour: ffmpeg does not read ICC profiles, so a non sRGB profile is treated as sRGB. Mirrored EXIF orientations (2, 4, 5, 7) are not corrected. `onFailure` marks the row `ingest_error`. Tests drive it with a folder standing in for R2 and the real ffprobe and ffmpeg (skipped when ffmpeg or libwebp is missing); `src/background-upload.e2e.test.ts` (outside `src/trigger` so it may import the routes' functions) runs the whole path against a small HTTP server standing in for R2: a signed PUT that refuses a wrong type or length, a HEAD for the size, the ingest reading the source through a URL with the real `downloadToFile`, then the list and the delete. The real R2 path is covered by the pipeline run.
- `cleanup` (every 15 minutes, UTC): fails abandoned uploads (judged by last activity, see below) and stale jobs, fails stuck background uploads (`failStuckBackgrounds`) and purges deleted uploads kept hidden past their link's life (`purgeRemovedBackgrounds`), expires takes, then drains `storage-deletion` (its own queue, concurrency 1; a row that fails 10 times is left for a person). A `queued` job older than `CLEANUP.queuedStaleMs` is failed as `stale_run` only when its run is no longer waiting: `failStaleJobs(db, now, isRunWaiting)` asks Trigger.dev (`isRunWaiting` in `src/lib/trigger-runs.ts`: QUEUED, DELAYED, DEQUEUED, PENDING_VERSION and EXECUTING count as waiting; an API error also counts, so a live job is never failed on a guess), so a job waiting behind its creator's limit survives; the backstop `CLEANUP.queuedBackstopMs` (6 hours) fails it regardless, and a queued job with no run ID is failed at 15 minutes as before. A `running` job past its usual limit (85 minutes, 50 for `transcribe`) is asked about too (`isRunAlive`, `failStaleJobs`'s fourth argument: any run that has not ended counts as alive, including `WAITING`; an API error counts as alive): Trigger.dev v4 keeps a retry that backs off or waits in its creator's queue as the same run, so it can start after the limit. It is failed only when the run has ended, has no run ID, or is past `CLEANUP.runningBackstopMs` (6 hours from `started_at`); the lookup cap is shared with the queued ones (merged least recently checked first). Two scans: the first (no lookup needed: running jobs with no run ID or past `CLEANUP.runningBackstopMs`, queued jobs without a run ID or past the backstop) never contains waiting jobs, so they cannot crowd a stale one out; the second asks about at most `CLEANUP.queuedRunChecksPerSweep` (25) runs, least recently checked first (a waiting job is touched, `updated_at`), each lookup limited to `CLEANUP.runCheckTimeoutMs` (5 s, a timeout counts as waiting), so a slow API takes about two minutes of the sweep at most. It starts by calling `ensureBuiltInBackgrounds(db, r2, { local: false })` (`built-in-backgrounds.ts`, spec 0008 AC-7): uploads the studio images and upserts their rows when a row is missing or differs (one query when all is in place), never the `testOnly` placeholder, and a failure is logged and does not stop the sweep. The images in `assets/backgrounds/` are bundled by `additionalFiles` in `trigger.config.ts` and read relative to the working directory. Also each run repairs missing product events and purges repeatable ones older than 13 months (spec 0016; a failure is logged and never stops the sweep). It also deletes API rate windows older than an hour (`purgeOldRateWindows`, spec 0018; same logged and never stops rule).
- `render-spike` is manual only and builds a 10 minute HDR fixture; it has no token guard. `sentry-check` throws inside `run()` only when its payload token matches `SENTRY_CHECK_TOKEN`. `hello` is the setup check.
- `ai-eval` (`src/trigger/ai-eval/`, spec 0017 AC-10): manual only, payload `{ "token": "<AI_EVAL_TOKEN>" }`, matched in constant time against `AI_EVAL_TOKEN` of the Trigger.dev env (`sentryCheckAllowed`); a wrong, missing or empty token, or no `AI_EVAL_TOKEN`, returns `skipped` before anything is read: no key, no model call. `runAiEval` (`run-eval.ts`, apart from Trigger.dev, the model and clock injected through `EvalIo`) runs the real model on every case of `tests/cut-quality/cases/index.ts` one after the other with `buildAiRequest`, `callClaude` (one retry on 429, 5xx, network) and the `AI_EDIT` settings, validates like the `ai_edit` step and scores with `scoreCuts`. An unusable answer (cut off, refused, not JSON, refused by `validateAiEdit`, failed call) scores the rules cuts, as production falls back, and the line names the cause (`fallback`). It logs numbers only: per case `caseId`, `holdout`, precision, recall, `wrongKeeps`, tokens in and out, seconds, `fallback`; then totals for `main`, `holdout` and `all`. The returned output adds `summary`, one entry per case (`id`, `holdout`, precision, recall, `fallback`, and `missed`, `wrongKeeps`, `cuts` as `start-end kind` strings in ms, built by the pure `buildCaseSummary`), so a miss can be found by its span. Never a prompt, word, reason, answer, error text, token or key, in the logs or the output. 1 attempt (a retry would pay for the set again), 30 minute maximum, never writes a file. Needs `ANTHROPIC_API_KEY` in the same env.

## Rules worth knowing

- Imports: job code may not import `@/app`, `@/server`, `next`, `react` or `@opennextjs/cloudflare` (ESLint in `eslint.config.mjs`, tested in `src/import-boundaries.test.ts`). Use `src/db/data/*` and `@/lib`.
- ffmpeg is pinned: `pinnedFfmpeg()` in `trigger.config.ts` installs one BtbN build and checks its SHA 256. To upgrade, change the URL and the hash together. Dev runs use the machine's own ffmpeg (`FFMPEG_PATH` and `FFPROBE_PATH` unset fall back to the bare names). CI installs the same build (`ci.yml`: the URL and hash are copied from `trigger.config.ts` and `src/ci-config.test.ts` keeps them equal; downloaded once per hash and cached, hash checked, put on the PATH) so the suites that run the real tools (`ingest-background.test.ts`, `src/background-upload.e2e.test.ts`, registered with `describeWithFfmpeg` from `src/test/ffmpeg.ts`) really run: with `CI` set a missing ffmpeg or ffprobe fails them with a message, on a developer's machine without them they are skipped with a note in the output. A new suite that needs the real tools uses the same helper, never `skipIf`.
- Render: constant frame rate (`-fps_mode cfr`, `outputFps` in `src/lib/trim.ts`), keep ranges snapped to frames (`alignToFrames`), HDR goes through `toneMapFilter` (zscale needs `tin=<transfer>` spelled out; `media.test.ts` covers it).
- Progress is throttled (`throttledProgress`: at most every 2 s and at least 1 point). Call `flush()` before the final step write. Render progress is scaled to 95.
- Retries: the default is 3 attempts and none in dev. `process-take` has 2 attempts and a 40 minute maximum (`PROCESS_TAKE_LIMITS`); `src/lib/cleanup-rules.ts` derives the stale job cutoff from them, so change both together. `probe` has 3; `sentry-check`, `ai-eval` and `render-spike` have 1.
- Failure codes are an open set in `src/lib/failure-codes.ts`: add, never rename or remove. `failureCodeFor` maps ffmpeg errors to `ffmpeg_error`, `DeadlineExceeded` (and Trigger's maximum duration) to `timeout` and the rest to `internal_error` (all refundable). A timed out ffmpeg is `ffmpeg_error`, not `timeout`. HRF-T10: the mappers (`failureCodeFor`, `transcribeFailureCode`) match an error by class and by `name`, because a failure hook can get a plain `{ name, message }` copy; each name is one constant in `src/lib/job-errors.ts` (`JOB_ERROR_NAMES`), used by the class and by the mapper, so a rename cannot make the mapper fall back to `internal_error`. A new job error class: add its name there and a row in `failure-code-table.test.ts`, which throws every error through both mappers. `finish()` refunds once (compare and swap) and the charge happens at `startJob`, so a retry never charges twice.
- ffmpeg input formats are pinned (RF3-T04, `src/lib/ffmpeg-input.ts`): the tools pick a demuxer from the content otherwise, so a text file named `.mp4` (an ffconcat script, say) could make them open another input. Every read of the original (`probeUrl`, `probeFile`, the thumbnail, silencedetect, waveform, render, keying frames, preview, transcript audio, the final gate's output frame) puts `ORIGINAL_INPUT` (`-f mov`) before `-i`; the stored background is `STORED_IMAGE_INPUT` (`-f image2`, the `-loop` demuxer) as a file and `STORED_IMAGE_URL_INPUT` (`-f jpeg_pipe`) over HTTP (`image2` refuses `-rw_timeout`); an uploaded background is read through `imageInputOfFile` (`media.ts`: `png_pipe`, `jpeg_pipe`, `webp_pipe` from the first bytes, `apng` when a PNG has an `acTL` chunk, because `png_pipe` would show only the first frame and hide the animation; none of those means refused, and so is a PNG with over 1000 chunks before its image data, which the `acTL` scan cannot clear). A new ffmpeg or ffprobe input takes its pin; the test is `input-formats.test.ts`, and a test source for the original must be an MP4 or MOV.
- Presigned URLs are secrets. `media.ts` rebuilds tool errors with only the tool name and exit code; never log a URL, key or payload.
- Job deadlines (`src/lib/deadline.ts`): Trigger.dev does not call `onFailure` for a run that exceeds `maxDuration` (seen in a local run: TIMED_OUT, job left active until the stale cleanup marks it `stale_run`). `process-take` and `transcribe-take` therefore wrap their work in `runWithDeadline(deadlineMs(maxDuration))` (stops 90 s early: the failure hooks need up to about 45 s, Sentry flush plus the database connect retries). The signal is passed down: `runFfmpeg` and the ffprobe calls kill the process (and settle only after it exited), `downloadToFile` and the Deepgram fetch abort, `uploadFileMultipart` starts no new part or retry (the back off wakes on the signal) and aborts the multipart upload (a part already in flight finishes), and each task's own `finally` removes its temp directory. After that `DeadlineExceeded` is thrown from inside `run()`, `failureCodeFor` maps it to `timeout` and the normal failure path finishes the job (refunded once for `process-take`; a transcribe job leaves the take Ready). A timed out attempt must not write after the deadline: `process-take` checks the signal before it commits a success, `runWithDeadline` rejects a late success, and its cut and render writes go through `whileJobActive` (`src/db/data/jobs/locks.ts`: locks the take, then the job, and rolls back unless the job is still queued or running), like `saveTranscriptAndFinish` for the transcript. New long work must take the signal and clean up in a `finally`; stale cleanup stays the backstop for a crashed worker. `probe` needs no deadline: its tool calls have their own 60 s limits (at most about 4 of them, under its 300 s) and the stuck upload recovery covers an overrun.
- Sentry: `jobFailureTags` adds `providerStatus` when the error has a numeric `status` (a refused Deepgram request, so a spending cap hit shows its 402), never the message. `init.ts` starts with no default integrations, and a global `tasks.onFailure` sends the allowlisted tags (`jobFailureTags`) and flushes. A payload that fails its schema never reaches `onFailure`, so test failures from inside `run()`. `process-take` and `probe` also have their own `onFailure` that writes database state.
- Product events (spec 0016): jobs cannot import `src/server`, so `src/trigger/analytics/record.ts` validates with `parseEventProps` (`src/lib/analytics-events.ts`) and writes through `insertAnalyticsEvent`. `recordTakeReady` runs after a video job finishes (`initial` and `rerender` only, never `background` or `transcribe`): it reads `aiEdit` from the job's persisted `ai_edit` step row with `aiEditOutcome` (never from the step's return value), counts the applied AI cuts, and writes `take_ready` plus, when the AI edit is `done`, `ai_edit_used`; both are once per take. `recordTakeFailed` runs in `onFailure` (only when this call really failed a video job) and on the probe task's failure paths (`limit_exceeded` there also records `limit_hit`). A failed write is logged with the event name and take ID and never changes a job.
- `usage-reconcile` (spec 0014 AC-11, B2-T37): manual, token gated like `ai-eval` (payload `{ "token": ... }` must equal `AI_EVAL_TOKEN`, else `skipped` with no database opened).
