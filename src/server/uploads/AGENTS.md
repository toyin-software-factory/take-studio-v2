# Uploads and R2 (src/server/uploads, src/lib/r2*.ts)

The browser uploads in parts straight to R2. Spec: [0004](../../../docs/specs/0004-core-take-loop/index.md). The numbers live in `src/lib/uploads.ts`.

- Sizes: 16 MiB parts (at most 128 for a 2 GiB file), at most 50 part links per request with no repeats, part links last 15 minutes. Jobs upload renders in 32 MiB parts with 3 attempts. In the browser each part gets 4 attempts, 3 parts run at once and links are refreshed 60 s early (`src/lib/upload-rules.ts`).
- Complete needs exactly `partCount` parts, numbered 1 to n in order. The server strips the quotes from ETags; `completeMultipartUpload` in `src/lib/r2.ts` puts them back, escapes them, and treats a 200 that contains `<Error>` as a failure (`R2CompleteError`). `InvalidPart`, `InvalidPartOrder` and `EntityTooSmall` give `bad_parts` (422). `NoSuchUpload` means it already completed, so the HEAD decides. A size mismatch fails the take with `corrupt_upload` and queues the key for deletion.
- A fresh complete answers `uploading` even on success: the take becomes `uploaded` only when the probe task runs `markUploaded`. A repeat call on a take that has moved on (`uploaded`, `processing`, `ready`, `expired`) answers its current status, so a client must not assume every success means `uploading`. A failed probe dispatch gives 503 `dispatch_failed`, and calling complete again is safe (the probe key is `probe-{takeId}`). Abort answers 409 once the object exists.
- CORS: browsers can read the ETag only because `r2-cors.json` exposes it. The allowed origins are listed in that file (the workers.dev URL and two localhost ports). A new origin needs an edit there and `pnpm r2:cors`, which overwrites the bucket's rules (`--check` only reads). Part links are query signed, so the browser sends raw bytes with no signed headers.
- Cleanup fails an upload after 60 minutes plus a 15 minute margin (`src/lib/cleanup-rules.ts`). That is the lifetime of the whole upload, not of one part link.
- Early refusal (spec 0014 AC-7, `earlyRefusal` in `http.ts`): `POST /api/uploads` answers 403 `limit_exceeded` (the four usage numbers in the body, `Cache-Control: private, no-store`) before any take or R2 upload exists when the limit is on and 0 seconds are left, or the optional `durationHintMs` is more than the seconds left. The hint is advisory only: it is never stored, a bad or missing one is ignored, and the probe's real duration decides at `startJob`. Nothing is refused while `usage_limit_enabled` is false, and a missing `USAGE_HASH_SECRET` or any read trouble lets the upload go on.
