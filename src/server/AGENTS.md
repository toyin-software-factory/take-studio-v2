# Server layer (src/server)

Creator scoped functions behind the routes in `src/app/api`. Specs: [0002](../../docs/specs/0002-data-model/index.md), [0004](../../docs/specs/0004-core-take-loop/index.md). The data functions underneath, the `Result` type and transactions are in [src/db/AGENTS.md](../db/AGENTS.md).

- Routes are thin: a `route.ts` calls a handler from `src/server/{uploads,takes}/http.ts` and exports `dynamic = "force-dynamic"`. The real dependencies (session, R2, Trigger.dev) come from the sibling `deps.ts`; tests call the handlers with injected deps.
- Each `http.ts` maps error codes to an HTTP status and a friendly message (`STATUS` and `MESSAGES`). Responses carry `cache-control: no-store`.
- Checks run in this order: Origin, then session, then ownership. Since spec 0018 step 3 the first two live in one place, `api-auth.ts` (`resolveCreator`, `guard`; real deps from `api-auth-deps.ts`), and the order is: an `Authorization` header present means the key alone is judged (401 `invalid_api_key`, never a fallback to the cookie, no Origin check, 120 requests a minute per key counted in the database, 429 `rate_limited` with `Retry-After`); no header means Origin on writes, then the session; then ownership. No `http.ts` builds its own session check and no `deps.ts` calls `getSession` (a test scans for it). The key check is an `UPDATE ... RETURNING` (so revoke is immediate and Hyperdrive never caches it) that also sets `last_used_at` at most hourly. Failed checks log `api_key_rejected` with a reason code only. Every route's deps now carry the shared guard (B2-T51, spec 0018 step 4); `src/server/api-parity.test.ts` compares the registry with each route by session and by key (same status and body), checks permissions and the allowance, and fails when a route is neither compared nor guard checked. Auth routes refuse a bearer header. Key routes stay session only. The text below is the session part. Origin must equal the origin of `BETTER_AUTH_URL`. It is checked on writes (POST, PATCH, DELETE); GET list, detail and media skip it.
- Ownership lives in the query (`eq(take.creatorId, creatorId)`; cuts and renders join through the take). Media links are presigned only after the ownership check and an R2 HEAD.
- Sessions: pages read the session through `getSession()` in `request.ts`, which also sets the Sentry user to `{ id }`. API routes use `getCreator` in each `deps.ts`, which does not set the Sentry user.
- Retention is 30 days from upload completion and never extended (`VIDEO_RETENTION_DAYS`). The cleanup sweep runs every 15 minutes, so `isExpired` (`src/lib/take-media.ts`) also counts a take past `videoExpiresAt` as expired before the sweep marks it: media links answer 410 and retry answers 409 at once. A `processing` take is not expired until its job ends.
- Upload limit: 10 per creator per hour, counting failed ones (429 `rate_limited`).
- Slow uploads stay alive (spec 0002 AC-18): `presignParts` touches `take.updated_at` through `touchUploading` (at most once a minute, only while the take is `uploading`, only after the ownership and part checks pass). The cleanup calls an `uploading` take abandoned when it is idle (no part links for `CLEANUP.uploadIdleMs`, the 15 minute link lifetime plus a 15 minute margin) or older than `CLEANUP.uploadBackstopMs` (6 hours); a browser that is still sending asks for fresh links at least every 15 minutes, so a 2 GB upload on a slow line is not failed. `failAbandonedUploads` still checks storage first, so a stored original (the upload completed) is left to `recoverStuckUploads`, which judges by `updated_at` too but only acts on a stored original, so the two rules do not clash. Both back off a take whose storage check throws by touching `updated_at`; only the 6 hour backstop (by `created_at`) ends such a take.
- Delete account (spec 0015 step 7, `account/policy.ts`): the control calls Better Auth's `deleteUser` (same `beforeDelete` path as spec 0002); `session.freshAge` is `ACCOUNT_DELETE_FRESH_SECONDS` (10 minutes), nothing else uses freshness, and an older session gets `SESSION_EXPIRED`. `account/delete-user.test.ts` runs the magic link round trip and the guard through the real handler.
- Email (spec 0006): `src/server/email/` holds the sign in limits, the signed turn off link (`/emails/off`: GET only redirects to a confirmation page, POST changes the setting, no session) and the take page switch API (`/api/account/email-prefs`, same guard and Origin check as takes). `POST /emails/off` never answers 500: the email env is read with `emailEnvSchema.safeParse` inside the guarded path (missing settings, an unreachable database or a rejected change give 400 for the one click and a redirect to `/emails/off/done?status=invalid` for the page; the log names the missing variables only). The sender and templates live in `src/lib/email/` because jobs use them too.
- Transcripts (spec 0007): `src/server/transcripts/` reads a transcript for its owner on the trimmed timeline (`getTrimmedForCreator`: words from `transcript`, removed ranges from the latest render, `take.duration_ms`, `source_fps`; `not_found` for another creator's take or no transcript) and serves `GET /api/takes/{id}/transcript/{txt|srt|vtt}` (ownership, then format: 404 before 422; `no-store`; the file body and headers come from `src/lib/transcript-download.ts`). It works on an expired take. The text is personal data: return it to the owner only, never log it.
- `POST /api/takes/{id}/transcript` is Make transcript / Try again (`makeTranscript`: Origin 403, session 401, owner 404, then 409 `job_active`, `original_gone`, `already_done`, `not_ready`; 202 `{ state: "making" }`; a trigger that throws finishes the job `trigger_failed` and answers 503). Retry answers `transcript_running` (the "still being made" message) while a transcribe job runs.
- `DELETE /api/takes/{id}` (spec 0013, `handleDelete`): Origin 403, session 401, then 404 for another creator's, a malformed or a missing ID (same body as every take route), 204 with no body on success, 404 on a repeat. It calls `deleteTake`, which commits the row removal and the `storage_deletion` keys in one transaction and then does the cancel of active runs and the drain request as best effort (`bestEffort` in `takes/index.ts`: a failure logs the take ID only and the answer stays 204; the sweep and the drain retry cover it). `TakeHttpDeps.afterDelete` lets tests replace both. Deleting is allowed while a job runs.
- `GET /api/takes/{id}/transcript` (session, then ownership; another creator's take is 404) returns `state`, `reason`, `canMake` and, when ready, the trimmed paragraphs and `version` (via `getTrimmedForCreator`), plus `edits` (the AI word fixes, undone ones included). `PATCH /api/takes/{id}/transcript/edits/{index}` `{ undone: boolean }` (spec 0012, `setEditUndone`): Origin 403, session 401, a bad body 422, then 404 (another creator's take, no transcript, a bad index, or no fix at that index). It locks the take then the transcript row, flips that one fix, bumps `transcript.updated_at` and returns `{ edit, version }`, so the caption track reloads. Never log transcript text or reasons. `state` is derived per request (transcript row, else the latest `transcribe` job). `getForCreator`'s `latestJob` ignores `transcribe` jobs so the progress view only follows video jobs.
- `GET /api/takes/{id}` (spec 0012 task 2) also returns `cuts[].reason`, `cuts[].proposedBy` (`rules`, `ai` or `creator`) and `aiEdit` (`done`, `unavailable` or null for older takes; from the latest succeeded `initial` or `rerender` job's `ai_edit` step) and `suggestion` (`{ backgroundId, name, reason }` or null: the AI's built in background pick, joined to `background.name`; null when none, when the background was deleted or is not built in). A cut reason and the suggestion reason can quote the take: never log them.
- Backgrounds (spec 0008): `PUT /api/takes/{id}/background` `{ backgroundId: id | "original" }` (`changeBackground` in `src/server/backgrounds`): Origin 403, session 401, body 422, then 404 (another creator's take, or a background that is not theirs and not built in) and 409 `job_active` ("A background change is already running. It'll show here when it's done.", or the transcript wording while a transcribe job runs), `original_gone`, `not_ready`, `same_background`, `background_not_ready`; 202 `{ jobId }`; a trigger that throws finishes the job `trigger_failed` and answers 503. `GET /api/takes/{id}` also returns `background` (the keyed background of the finished video or null), `noGreenScreen` and `backgroundJob` (the latest `background` job and its `targetBackgroundId`, so "Try again" repeats that change). `noGreenScreen` comes from the latest render's snapshot or from a running or succeeded job that skipped the green screen, never from a failed or cancelled one. Cost guard (HRF-T01): also `409 no_green_screen` for a real background when the latest render found no green screen (the original is not refused for it; the note is `NO_GREEN_SCREEN_NOTE`) and `429 background_change_limit` after 10 background changes started by the creator in an hour (failed ones and retries count; `BACKGROUND_CHANGE.perHour`).
- Changes (spec 0011, `src/server/changes/`): `POST /api/takes/{id}/changes` `{ baseRenderId, background?: { id | null }, cuts?: [{ id, applied }] }` (Origin 403, session 401, body 422, then 404 and 409 `stale`, `nothing_changed`, `job_active`, `original_gone`, `invalid_transition`, `no_green_screen`, `background_not_ready`, `background_missing`, 422 `invalid`, 429 `change_limit`, 503 `dispatch_failed`; 202 `{ jobId }`); `GET /api/takes/{id}/jobs/{jobId}` returns `{ status }` for this creator's take only (404 otherwise); `GET /api/takes/{id}/waveform` returns `{ waveform }` (null until computed). `GET /api/takes/{id}` also returns `cuts` (`{ id, startMs, endMs, kind, applied }`), `originalAvailable` and `latestRender.removedRanges`. Messages are `CHANGE_MESSAGES` in `src/lib/change-messages.ts` (not `take-messages.ts`: that file is imported by `take-display.ts`, so importing `take-display` back made a cycle that broke the Worker build).
- Backgrounds (spec 0008): `src/server/backgrounds/library.ts` (with `library-http.ts` and `library-deps.ts`) lists what a creator can pick (`GET /api/backgrounds`: `builtIn`, `mine` newest first (max 100) and `defaultId`, each item `{ id, name, alt, status, thumbUrl }` with a 1 hour presigned thumbnail). `defaultId` is an addition to the spec's response shape: the creator's last pick read from `user.default_background_id`, null when it was deleted or is not ready, so the upload area can preselect without another read. Upload create (`POST /api/uploads`) takes an optional `backgroundId` (an ID or `original`): in the creator's transaction it locks the creator, then the background (`FOR KEY SHARE`), then creates the take, and stores `take.background_id` and `user.default_background_id` together; 404 `background_not_found` for an unknown or another creator's background, 409 `background_not_ready`. Left out means no choice and no change to the default.
- Uploaded backgrounds (spec 0008, AC-8 to AC-10): `src/server/backgrounds/upload.ts`, `upload-http.ts` and `upload-deps.ts`. `POST /api/backgrounds` (name 1 to 80, `contentType` image/jpeg, image/png or image/webp, `bytes` up to 10 MiB; 20 started per hour, failed ones counted; library cap 100 → 409 `library_full`) returns a presigned PUT whose content type and exact length are signed (`presignPutObject`, 15 minutes). `POST /api/backgrounds/{id}/complete` checks the source is stored (HEAD), moves `uploading` to `processing` and triggers `ingest-background` (key `ingest-{id}`; a trigger failure fails the row `ingest_error` and answers 503). `DELETE /api/backgrounds/{id}` is 404 for built ins and other creators' IDs, 409 `in_use` while a queued or running job has `target_background_id` = this background (required: the FK `ON DELETE SET NULL` would clear the job's target and the worker could not tell that from Keep original), else queues the three files and the preview stills and answers 204. Every one checks Origin. The list items also carry `failureCode` (additive) so the picker can show the friendly reason. The presigned PUT stays valid 15 minutes, so deleting an upload that is still `uploading` and younger than 20 minutes keeps a hidden `failed`/`removed` row (not listed, cannot be completed) and queues the keys now; the cleanup (`purgeRemovedBackgrounds`) queues them again after the link has expired and deletes the row, so a late PUT cannot leave an orphan source file. Account deletion cannot keep a row (the user row cascades), so there a PUT sent after deletion within 15 minutes of an unfinished upload can still leave one source file (at most 10 MB, under the deleted creator's own prefix).
- Previews (spec 0008): `POST /api/takes/{id}/background/preview` `{ backgroundId }` (`startPreview`, `preview-http.ts`): Origin 403, session 401, body 422 (a background ID; "Original" never calls this), 404, 409 `original_gone` / `not_ready` / `background_not_ready`; 200 with `{ state: "ready", url, noGreenScreen }` for a cache hit (1 hour link), 202 `{ state: "making" }` otherwise; a trigger that throws marks the preview `failed` and answers 503 so the next ask starts it again. `GET` with `?backgroundId=` is the same view read only (404 when none was asked for, 409 `original_gone` for an expired take, whose stills are being deleted).
- `GET /api/usage` (spec 0014 AC-8, `src/server/usage/`): session 401 (no Origin check, a read), then `{ usedSeconds, allowanceSeconds, remainingSeconds, resetsOn }` for the current UTC month, and nothing else (no email, no hash). A missing `USAGE_HASH_SECRET` is a friendly 503. Every response, and every `limit_exceeded` body, is sent `Cache-Control: private, no-store` (`PRIVATE_NO_STORE`), not plain `no-store`. `usageForCreator` is the one place that turns the session user's email into the hash and reads the numbers; use it, never rebuild it. Retry at the limit (`handleRetry`): 403 `limit_exceeded` with the dated `limitExceededMessage` (reset date and the take's expiry) and the four numbers, nothing charged; retry works again once the month turns or the allowance setting is raised.
- `POST /mcp` (spec 0019 steps 1 to 3, `src/server/mcp/`, route `src/app/mcp/route.ts`): the MCP server over stateless Streamable HTTP, one JSON message per request, built on `@modelcontextprotocol/sdk` (the web standard transport, JSON responses). `handleMcp` checks the key first (no `Authorization` header or a bad key is 401 with `WWW-Authenticate` pointing at the protected resource document, never a cookie fallback), counts the POST against the key's 120 a minute, then `checkBody` (over 256 KB is 413, a batch or non object is `-32600`). There is no tool list to keep by hand: a tool is a registry route flagged `mcp` in `api-registry.ts` (`tools.ts` derives `TOOLS`: path parts plus the route's own zod request schema as input, a plain description, annotations, the delete guard). `dispatch.ts` builds an internal `Request` for the route (path values URL encoded, query on a GET, JSON body otherwise) with the caller's own `Authorization` header and runs the exported handler wired in `handlers.ts` (`buildHandlers`, keyed by `routeKey`; the real factories are passed in `deps.ts`, the tests' in `test-deps.ts`), so the route's checks, ownership query and limits apply and tools hold no limit logic. The one rule `dispatch.ts` owns is the delete guard: `delete_take` without `confirm: true` answers `confirmation_required` and never calls the route. Routes left out (browser only uploads, email preferences) are in `MCP_EXCLUSIONS` with a reason. To add a tool: add the name to `MCP_TOOL_NAMES`, flag the route in `MCP_TOOLS`, add its text in `tools.ts`, wire its handler in `handlers.ts`; `tools.test.ts` fails on any mismatch, and `tools-routes.test.ts` holds the ownership, same answer and delete tests. A `tools/call` therefore spends two of the key's 120 a minute (the POST, then the route). Logs carry the tool name, take ID, creator ID, route status and duration only, never arguments, results, links or keys. Every response is `Cache-Control: private, no-store`; GET and DELETE are 405.
- `POST /api/realtime/token` (spec 0021 step 2, `src/server/realtime/`): mints a 60 second Deepgram token for the recorder's voice following. Order: Origin 403, any `Authorization` header 401 `session_required` (session only, listed as an exclusion in the API registry), session 401, `DEEPGRAM_REALTIME_API_KEY` missing 503 (a separate spend capped Worker secret, optional in the deploy preflight, never `DEEPGRAM_API_KEY`), usage used up 403 `limit_exceeded` (skipped when `USAGE_HASH_SECRET` is missing), then `reserveMint` (10 an hour and 40 a day per creator, 429 `rate_limited` with `Retry-After`; a refused call writes nothing), then Deepgram's `/v1/auth/grant` (failure 503; logs a status code or error name only). Answers `{ token, expiresInSeconds }` with `private, no-store`. The token is a secret: never log it. `purgeOldMints` in the cleanup job deletes rows older than two days.
- Analytics (spec 0016, `src/server/analytics/`): `recordEvent(db, event)` validates props with the registry in `src/lib/analytics-events.ts`, never throws and returns a `Result` (`invalid` or `failed`; the log carries the event name and take ID only). Call it after the work has committed, never inside the user's transaction. `signup` is written from Better Auth's `databaseHooks.user.create.after` in `auth.ts`. `funnel(db, window)` in `report.ts` returns counts only (the queries are in `report-queries.ts`: distinct creators, the second take, the AI edit share, failures by code; `foundingMembers` is all time). Call sites (spec 0016 steps 3 and 4): `completeUpload` records `take_uploaded` right after the size check and before the probe is dispatched, the media route records `take_downloaded` only for `kind=download`, the transcript download route records `transcript_downloaded` with `transcript_txt`, `_srt` or `_vtt`, `startChanges` records `change_requested` after the dispatch, and the early upload refusal (`upload_start`, no take) and the retry refusal (`upload_complete`) record `limit_hit`. Each is one awaited `recordEvent` that cannot change the answer. Spec 0017 step 4: right after `take_downloaded` the media route calls `recordCutsReviewed` (`analytics/cuts-reviewed.ts`), one `cuts_reviewed` snapshot of counts per cut proposer and kind from the take's `cut` rows (numbers only, best effort, repeat downloads write repeat rows); `/insights` reads the latest per take (`latestCutSnapshots`). The counts add a fifth field, `kept`, to the spec's four (the restore rate's denominator).
- API keys (spec 0018 step 2, `src/server/api-keys/`): `POST /api/keys` `{ name }` (Origin 403, then 401 `session_required` for any request with an `Authorization` header, then session 401, 422, 409 `key_limit`; 201 `{ id, name, prefix, key, createdAt }`, the only place the raw key exists), `GET /api/keys` and `DELETE /api/keys/{id}` (204; another creator's, a malformed, a missing ID or a repeat is the same 404). Session only, never a bearer, and every answer is `Cache-Control: private, no-store`. The data functions in `db/data/api-keys.ts` take the hash and prefix, never the key; create locks the `user` row `FOR UPDATE` and counts, so concurrent creates cannot pass 5. Nothing here logs.
- Multipart upload and R2 rules: [src/server/uploads/AGENTS.md](uploads/AGENTS.md).
- `POST /api/takes/{id}/missed` `{ atMs }` (spec 0017 step 6, `takes/missed.ts`): Origin 403, session 401, 404 (missing or not yours), 409 `not_markable` (not `ready` or expired), 422 (`atMs` not an integer 0..edited length; the edited length is `take.duration_ms` minus applied cuts, derived here), 204. Records `cut_missed` with `atMs` rounded to 100 ms and `durationMs`; never writes a cut or starts a job. At most `MISSED_MARK.perTakePerDay` (20) per take per UTC day: the rest answer 204 without writing.
- Take source and script (spec 0021): `takes.create` stores `source` (default `file`) and a trimmed `script` (`cleanScript`); the take GET returns both (`takeView`). Deleting a take deletes its script; expiring the video does not.
