# Server layer (src/server)

Creator scoped functions behind the routes in `src/app/api`. Specs: [0002](../../docs/specs/0002-data-model/index.md), [0004](../../docs/specs/0004-core-take-loop/index.md). The data functions underneath, the `Result` type and transactions are in [src/db/AGENTS.md](../db/AGENTS.md).

- Routes are thin: a `route.ts` calls a handler from `src/server/{uploads,takes}/http.ts` and exports `dynamic = "force-dynamic"`. The real dependencies (session, R2, Trigger.dev) come from the sibling `deps.ts`; tests call the handlers with injected deps.
- Each `http.ts` maps error codes to an HTTP status and a friendly message (`STATUS` and `MESSAGES`). Responses carry `cache-control: no-store`.
- Checks run in this order: Origin, then session, then ownership. Origin must equal the origin of `BETTER_AUTH_URL`. It is checked on writes (POST, PATCH, DELETE); GET list, detail and media skip it.
- Ownership lives in the query (`eq(take.creatorId, creatorId)`; cuts and renders join through the take). Media links are presigned only after the ownership check and an R2 HEAD.
- Sessions: pages read the session through `getSession()` in `request.ts`, which also sets the Sentry user to `{ id }`. API routes use `getCreator` in each `deps.ts`, which does not set the Sentry user.
- Retention is 30 days from upload completion and never extended (`VIDEO_RETENTION_DAYS`). The cleanup sweep runs every 15 minutes, so `isExpired` (`src/lib/take-media.ts`) also counts a take past `videoExpiresAt` as expired before the sweep marks it: media links answer 410 and retry answers 409 at once. A `processing` take is not expired until its job ends.
- Upload limit: 10 per creator per hour, counting failed ones (429 `rate_limited`).
- Slow uploads stay alive (spec 0002 AC-18): `presignParts` touches `take.updated_at` through `touchUploading` (at most once a minute, only while the take is `uploading`, only after the ownership and part checks pass). The cleanup calls an `uploading` take abandoned when it is idle (no part links for `CLEANUP.uploadIdleMs`, the 15 minute link lifetime plus a 15 minute margin) or older than `CLEANUP.uploadBackstopMs` (6 hours); a browser that is still sending asks for fresh links at least every 15 minutes, so a 2 GB upload on a slow line is not failed. `failAbandonedUploads` still checks storage first, so a stored original (the upload completed) is left to `recoverStuckUploads`, which judges by `updated_at` too but only acts on a stored original, so the two rules do not clash. Both back off a take whose storage check throws by touching `updated_at`; only the 6 hour backstop (by `created_at`) ends such a take.
- Email (spec 0006): `src/server/email/` holds the sign in limits, the signed turn off link (`/emails/off`: GET only redirects to a confirmation page, POST changes the setting, no session) and the take page switch API (`/api/account/email-prefs`, same guard and Origin check as takes). `POST /emails/off` never answers 500: the email env is read with `emailEnvSchema.safeParse` inside the guarded path (missing settings, an unreachable database or a rejected change give 400 for the one click and a redirect to `/emails/off/done?status=invalid` for the page; the log names the missing variables only). The sender and templates live in `src/lib/email/` because jobs use them too.
- Transcripts (spec 0007): `src/server/transcripts/` reads a transcript for its owner on the trimmed timeline (`getTrimmedForCreator`: words from `transcript`, removed ranges from the latest render, `take.duration_ms`, `source_fps`; `not_found` for another creator's take or no transcript) and serves `GET /api/takes/{id}/transcript/{txt|srt|vtt}` (ownership, then format: 404 before 422; `no-store`; the file body and headers come from `src/lib/transcript-download.ts`). It works on an expired take. The text is personal data: return it to the owner only, never log it.
- `POST /api/takes/{id}/transcript` is Make transcript / Try again (`makeTranscript`: Origin 403, session 401, owner 404, then 409 `job_active`, `original_gone`, `already_done`, `not_ready`; 202 `{ state: "making" }`; a trigger that throws finishes the job `trigger_failed` and answers 503). Retry answers `transcript_running` (the "still being made" message) while a transcribe job runs.
- `GET /api/takes/{id}/transcript` (session, then ownership; another creator's take is 404) returns `state`, `reason`, `canMake` and, when ready, the trimmed paragraphs and `version` (via `getTrimmedForCreator`). `state` is derived per request (transcript row, else the latest `transcribe` job). `getForCreator`'s `latestJob` ignores `transcribe` jobs so the progress view only follows video jobs.
- Backgrounds (spec 0008): `PUT /api/takes/{id}/background` `{ backgroundId: id | "original" }` (`changeBackground` in `src/server/backgrounds`): Origin 403, session 401, body 422, then 404 (another creator's take, or a background that is not theirs and not built in) and 409 `job_active` ("Your video is still being made", or the transcript wording while a transcribe job runs), `original_gone`, `not_ready`, `same_background`, `background_not_ready`; 202 `{ jobId }`; a trigger that throws finishes the job `trigger_failed` and answers 503. `GET /api/takes/{id}` also returns `background` (the keyed background of the finished video or null), `noGreenScreen` and `backgroundJob` (the latest `rerender` with no trim step and its `targetBackgroundId`, so "Try again" repeats that change). `noGreenScreen` comes from the latest render's snapshot or from a running or succeeded job that skipped the green screen, never from a failed or cancelled one. Cost guard (HRF-T01): also `409 no_green_screen` for a real background when the latest render found no green screen (the original is not refused for it; the note is `NO_GREEN_SCREEN_NOTE`) and `429 background_change_limit` after 10 background changes started by the creator in an hour (failed ones and retries count; `BACKGROUND_CHANGE.perHour`).
- Backgrounds (spec 0008): `src/server/backgrounds/library.ts` (with `library-http.ts` and `library-deps.ts`) lists what a creator can pick (`GET /api/backgrounds`: `builtIn`, `mine` newest first (max 100) and `defaultId`, each item `{ id, name, alt, status, thumbUrl }` with a 1 hour presigned thumbnail). `defaultId` is an addition to the spec's response shape: the creator's last pick read from `user.default_background_id`, null when it was deleted or is not ready, so the upload area can preselect without another read. Upload create (`POST /api/uploads`) takes an optional `backgroundId` (an ID or `original`): in the creator's transaction it locks the creator, then the background (`FOR KEY SHARE`), then creates the take, and stores `take.background_id` and `user.default_background_id` together; 404 `background_not_found` for an unknown or another creator's background, 409 `background_not_ready`. Left out means no choice and no change to the default.
- Uploaded backgrounds (spec 0008, AC-8 to AC-10): `src/server/backgrounds/upload.ts`, `upload-http.ts` and `upload-deps.ts`. `POST /api/backgrounds` (name 1 to 80, `contentType` image/jpeg, image/png or image/webp, `bytes` up to 10 MiB; 20 started per hour, failed ones counted; library cap 100 → 409 `library_full`) returns a presigned PUT whose content type and exact length are signed (`presignPutObject`, 15 minutes). `POST /api/backgrounds/{id}/complete` checks the source is stored (HEAD), moves `uploading` to `processing` and triggers `ingest-background` (key `ingest-{id}`; a trigger failure fails the row `ingest_error` and answers 503). `DELETE /api/backgrounds/{id}` is 404 for built ins and other creators' IDs, 409 `in_use` while a queued or running job has `target_background_id` = this background (required: the FK `ON DELETE SET NULL` would clear the job's target and the worker could not tell that from Keep original), else queues the three files and the preview stills and answers 204. Every one checks Origin. The list items also carry `failureCode` (additive) so the picker can show the friendly reason. The presigned PUT stays valid 15 minutes, so deleting an upload that is still `uploading` and younger than 20 minutes keeps a hidden `failed`/`removed` row (not listed, cannot be completed) and queues the keys now; the cleanup (`purgeRemovedBackgrounds`) queues them again after the link has expired and deletes the row, so a late PUT cannot leave an orphan source file. Account deletion cannot keep a row (the user row cascades), so there a PUT sent after deletion within 15 minutes of an unfinished upload can still leave one source file (at most 10 MB, under the deleted creator's own prefix).
- Previews (spec 0008): `POST /api/takes/{id}/background/preview` `{ backgroundId }` (`startPreview`, `preview-http.ts`): Origin 403, session 401, body 422 (a background ID; "Original" never calls this), 404, 409 `original_gone` / `not_ready` / `background_not_ready`; 200 with `{ state: "ready", url, noGreenScreen }` for a cache hit (1 hour link), 202 `{ state: "making" }` otherwise; a trigger that throws marks the preview `failed` and answers 503 so the next ask starts it again. `GET` with `?backgroundId=` is the same view read only (404 when none was asked for, 409 `original_gone` for an expired take, whose stills are being deleted).
- Multipart upload and R2 rules: [src/server/uploads/AGENTS.md](uploads/AGENTS.md).
