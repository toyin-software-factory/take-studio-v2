# Data layer (src/db)

Drizzle over Postgres. Spec: [0002 data model](../../docs/specs/0002-data-model/index.md).

## Layers and rules

- `src/db/data/*` are system functions: they act on IDs only and are safe for jobs. `src/server/*` wraps them for a creator (it takes `creatorId` from the session). Job code imports `src/db/data`, never `src/server`.
- Expected failures return a `Result` (`src/lib/result.ts`: `ok`, `err`). Another creator's resource and a malformed ID both give `not_found`, never "forbidden".
- A take's status changes only through `transitionTake` (compare and swap on the old status; the rules are `TAKE_TRANSITIONS` in `src/lib/take-rules.ts`). One known exception: `expireTake` in `data/deletion.ts` writes `expired` itself after a row lock.
- Transactions: `runTx(db, fn)` in `src/db/tx.ts`. `fn` returns a `Result`; `{ ok: false }` rolls back and comes back as a normal result, a thrown error rolls back and propagates, and an open transaction becomes a savepoint. Data functions take an `Executor` (`Db | Tx`) so they compose; `pgErrorCode` reads the SQLSTATE even when Drizzle wraps the error.
- Job code map (`src/db/data/jobs/`, imported as `@/db/data/jobs` through `index.ts`, no file past about 250 lines): `initial.ts` (`startJob` for `initial` and `rerender`, `finishVideoJob`: flip or discard renders, move the take, refund once), `transcribe.ts` (`startTranscribeJob`, `finishTranscribeJob`), `change.ts` (`startChangeJob`, `legacyBackgroundRerender`), `background.ts` (`finishBackgroundJob`: success flips the render, sets `take.background_id`, applies the `cut_plan`), `finish.ts` (`finish`, `finishInTx`: validate, lock, job compare and swap, then dispatch by kind), `start-shared.ts` (`startJobRow` inserts the job and its steps; `runStart` runs the transaction and turns the one active job per take unique violation into the caller's conflict error, the only place that handles it), `locks.ts` (`lockTakeForJob`: background key share then take, `whileJobActive`), `steps.ts` (`markRunning`, `updateStep`), `render-files.ts` (`flipLatestRender`, `discardJobRenders`, `queueDeletions`), `types.ts`. A new job kind adds its own file with a start and a finish function, one `startJobRow` call, one branch in `finish.ts`, and goes through `runStart`.
- Constraint names that code checks (SQLSTATE plus constraint name) are exported constants in `src/db/schema/constraint-names.ts`, used by the schema that creates the constraint and by the check (`ONE_ACTIVE_JOB_INDEX` in `runStart`), and by the migration test. A new checked constraint gets its constant there.
- Job kinds: `startJob` moves the take to `processing` and charges; a `transcribe` job (spec 0007) works beside a `ready` take. `startTranscribeJob` locks the take, refuses `original_gone`, `already_done`, `job_active` and `invalid_transition`, charges 0 and never moves the take. `finishInTx` for a transcribe job sets only the job status and code: no take transition, no render flip or discard, no refund. `expireTake` and `expireDueTakes` skip any take with a queued or running job of any kind. The `transcript` table (one row per take, cascade deleted, words with times on the original) is read and written through `data/transcripts.ts`; its text is personal data, never log it.
- **Lock order: creator, then background (spec 0008), then take, then job, then the rows under them (renders, cuts, steps, previews).** A path that locks a background takes it `FOR KEY SHARE` before the take (`startJob` reads the take's background first, `whileJobActive` locks the job's `target_background_id`); deleting a background locks the creator row first (its default background foreign key updates it) and then the background `FOR UPDATE`, then the takes and jobs that reference it. Every path that locks both a take and a job takes the take first: `startJob` and `startTranscribeJob` (take lock, then insert), take and creator deletion (take lock, then the job rows go), `finishInTx` (it locks the take before it changes the job, so the cleanup sweep, `onFailure` and cancel all follow), `jobs.cancel`, `saveTranscriptAndFinish` and `whileJobActive`. Never lock a job and then wait for its take: it deadlocks against deletion. `src/server/lock-order.test.ts` runs the pairs at the same time and fails on a Postgres deadlock (40P01).
- Backgrounds (spec 0008): `background` (built ins have `creator_id` null; a `ready` row must have `image_key`, `thumb_key`, `width` and `height`, a CHECK), `background_preview`, and the references `take.background_id`, `processing_job.target_background_id`, `render.background_id` and `user.default_background_id`, all ON DELETE SET NULL (a render keeps `background_name`, `keyed` and `key_color`). `user.default_background_id` is a plain Drizzle column on Better Auth's table: never an `additionalFields` entry, always read from the database. `startJob` copies `take.background_id` to the job and adds the `background` step.
- A background change (spec 0008) and cut changes (spec 0011): `startChangeJob` (`data/jobs/change.ts`, the one start for both; `PUT /background` is a wrapper with no cuts and no `baseRenderId`) takes the named, or else the latest render's inherited, background `FOR KEY SHARE`, then the take, and starts a free job of kind `background` (not `rerender`, which keeps its meaning: a re render started by `startJob`) with `target_background_id` and the steps `background` (only for a real background) and `render`, leaving the take `ready`. Refusals: `not_found` (another creator's take or background, unknown ID), `background_not_ready`, `invalid_transition` (take not ready), `original_gone`, `job_active`, `no_green_screen` (a real background when the latest render has a `background_name` but `keyed` false; the original is not refused for it), `background_change_limit` (10 per creator per hour, `BACKGROUND_CHANGE.perHour`: `background` jobs (plus the legacy `rerender` rule below) counted from `processing_job` through `take.creator_id`, failed ones and retries included; the creator row is locked first, so lock order is creator, background, take, job), `nothing_changed` (no cut entry differs from its stored `applied` and the effective background equals the latest render's `keyed ? background_id : null`; no failed job exemption, a failed change leaves the state unchanged so the same request is a plain retry), `stale` (`baseRenderId` is not the latest render), `background_missing` (cut only request while the inherited background is gone), `invalid` (the plan would remove the whole take); the limit is shared by cut and background changes. **`processing_job.cut_plan`** (jsonb `{cutId, applied}[]`, null for none; entries equal to the stored state are dropped) is read by `renders.create` from the locked job row for the snapshot and applied by `finishInTx` on success only (`applied` and `creator_changed_at` = the job's `finished_at`, `WHERE id AND take_id`), after a `render_mismatch` safety check. `take.waveform` (jsonb, filled by a later task) is read by `GET /waveform`. `finishInTx` decides with `isBackgroundChange(kind, takeStatus)`: a `background` job never moves the take or refunds (LEGACY, until a later cleanup task: a `rerender` on a take that is not `processing` counts too, because an old Worker may have started it during the deploy; the hourly count and the latest change lookup likewise count a `rerender`, `legacyBackgroundRerender` in `jobs/background.ts`; migration 0007 only widens the kind CHECK and converts no row, because a `rerender` never has a `trim` step (`updateStep` only updates existing rows) so old background changes cannot be told from a `startJob` re render afterwards; a later cleanup task converts them once a rule is proven on the data); success flips the latest render and sets `take.background_id` from the new render's own snapshot (not from `target_background_id`, which a background delete clears), failure or cancel keeps the take, its latest render and its background and only queues the job's own render files. `finishInTx` and `jobs.cancel` take the job's target background `FOR KEY SHARE` before the take (lock order), tested against a background delete (`cancel` in `src/server/backgrounds/background.test.ts`). `renders.create` records no reference (name and colour kept) when the background was deleted since the job loaded it, instead of failing on the foreign key. A keyed render whose background was deleted (reference null, name kept) is not "the original": `startChangeJob` lets the take go back to the original or pick another. **Deleting a background must refuse (409 `in_use`) while a queued or running job targets it** (spec 0008 AC-10, S3S-T05): the foreign key clears `target_background_id`, and the worker cannot tell that from "Keep original", so it would render the original instead of failing `background_missing`.
- Previews (spec 0008, `data/previews.ts`): `requestPreview` locks the background `FOR KEY SHARE`, then the take, and reuses the row of the take's current cut version (`cutVersion` of the applied cut ranges, `src/lib/background-preview.ts`): `ready` is a cache hit and a fresh `making` is left alone (neither dispatches), `failed` or a `making` older than `PREVIEW_STALE_MS` (8 minutes, derived from the job limits) is reset on the same row and dispatched, none inserts. `completePreview` holds a share lock on the take (so it waits for an expiry, which locks it `FOR UPDATE` and queues the preview keys) and writes only while the row exists, the take is not expired and the row is `making`: `gone` (row or take gone, or expired: the job removes its file) or `superseded` (a retry finished the row, which owns the same derived key: the job leaves the file). `failPreview` only changes a `making` row. `getPreview` and `loadPreviewWork` treat an expired take as `original_gone` / no work. `takeFileKeys` includes every preview's derived key, so take and account deletion queue the stills. Deleting a background still has to queue the stills of its previews (S3S-T05).
- `whileJobActive(db, jobId, fn, signal?)` (`data/jobs/locks.ts`) fences the writes a job attempt makes beyond its own rows (`process-take`: cuts, render create and complete): one transaction that locks the take, then the job, requires the job queued or running (`job_final` otherwise) and, with a signal, rolls back if the deadline fired before or during `fn` (`aborted`). A timed out attempt whose job `onFailure` or the cleanup already failed therefore writes nothing. `saveTranscriptAndFinish` does the same for the transcript.
- Uploaded backgrounds (spec 0008): `data/backgrounds.ts`. `createBackgroundUpload` locks the creator row for the 20 per hour and 100 kept limits; `deleteBackground` locks the background `FOR UPDATE` first and refuses (`in_use`) while any queued or running job targets it; `deleteCreatorBackgrounds` runs inside the account deletion transaction before the takes are locked; `failStuckBackgrounds` fails rows `uploading` or `processing` for over an hour (`skipLocked`) and queues their keys; `deleteBackground` keeps a hidden `failed`/`removed` row for an `uploading` upload under 20 minutes old (its presigned PUT may still be live) and `purgeRemovedBackgrounds` queues its keys once more after that and deletes it; `saveIngest` re-reads the row under a lock and answers `gone` for a deleted or already failed row. Every delete queues the three files (`backgroundKeys`) and any preview still.
- Row locks are the concurrency guard: the upload rate limit locks the creator row, cut edits lock the take, cancel locks the job. Keep those checks inside the transaction.

## Clients

- Web: `createWebDb` builds a new client per request over Hyperdrive (`max: 5`, `fetch_types: false`). Never keep one at module level; `getDb()` in `src/server/request.ts` is the way in.
- Jobs: `withJobDb` opens and closes a client inside each task (`max: 2`, the Neon pooled URL, first connect retried 3 times for scale to zero).

## Tests and migrations

- `openTestDb()` (`src/db/testing/test-db.ts`) refuses any host but localhost, creates the database if it is missing and applies `drizzle/`. It needs `pnpm db:up`. A test that sweeps whole tables passes its own `{ database: "take_studio_test_<name>" }`. `createCreator` and `seedTake` insert rows directly (`seedTake` defaults to `uploaded`).
- After a schema change run `pnpm db:generate` and commit `drizzle/`; CI fails if generate would change it. `schema/migration.test.ts` checks the generated SQL text (drizzle-kit has dropped partial index WHERE clauses before), so run it after you regenerate. Deploys migrate before the code ships, so migrations must be backward compatible. The connection guard is `scripts/db-guard.ts` (see root `AGENTS.md`).
