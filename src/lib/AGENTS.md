# Shared rules (src/lib)

Mostly pure modules used by the web app, the browser, the Worker and the jobs. Specs: [0002](../../docs/specs/0002-data-model/index.md), [0004](../../docs/specs/0004-core-take-loop/index.md), [0005](../../docs/specs/0005-error-monitoring.md). The modules that matter most to a job, an upload or a route are described in [src/trigger](../trigger/AGENTS.md), [src/db](../db/AGENTS.md), [src/server](../server/AGENTS.md) and [src/components/takes](../components/takes/AGENTS.md); this file covers what is shared.

## What lives where

- Rules and registries: `take-rules`, `take-media`, `cleanup-rules`, `cut-rules`, `cuts`, `billing`, `processing`, `failure-codes`, `uploads`, `upload-rules`.
- Media: `probe` (ffprobe JSON to facts), `trim` (silence to cuts, ffmpeg filter scripts, progress).
- `storage-lifecycle` (spec 0013, pure): the R2 backstop rules (`lifecycleRules()`: delete under `originals/`, `renders/`, `previews/` after `BACKSTOP_DAYS` = 35, abort incomplete multipart uploads after 2 days, never `backgrounds/`). The day count is one constant; its test fails unless it is greater than `VIDEO_RETENTION_DAYS`, so the app's own 30 day cleanup always runs first. Applied by `scripts/apply-r2-lifecycle.sh`.
- Storage and jobs: `r2` (S3 API through aws4fetch), `r2-file-upload` (Node only, for jobs), `trigger-runs`.
- `keying` (spec 0008, pure): green screen detection on raw RGB frames (16 border patches, HSV rules, key colour median; `DETECTION`) and the chroma key filter lines (`compositeFilters`, `KEYING`); `renderFilterScript(keep, { hdr, hasAudio, background })` in `trim.ts` calls it. The ffmpeg side is `src/trigger/keying.ts`. S3S-T10: the chroma key is adaptive. ffmpeg's `chromakey` compares only U and V, so a pale or dark green sits near neutral and grey, skin and dark clothing fall inside a fixed window and are keyed out with the screen. `keySettings(key)` scales similarity (0.3 times) and blend (0.22 times) with `keyChroma(key)`, the key's distance from neutral, capped at the old 0.12 and 0.08 (a saturated green is unchanged); a key under `KEYING.minChroma` (0.12) is `low_chroma`, so no green screen; `detectGreenScreen` and `detectInFrame` return `reason` on an unusable result. `DETECTION.minSaturation` is 0.2 (pale mint counts as green, the chroma floor keeps grey walls out). `frameAlphaArgs` and `transparentShare` let a job ask ffmpeg itself what the key would remove: more than `KEYING.maxKeyedShare` (85 %) of a frame transparent (`erasesSubject`) means the take is treated as no green screen. S3S-T12: `compositeFilters` starts the keyed frames at time 0 (`setpts=PTS-STARTPTS`). `overlay` pairs a frame of each input by time and the background image is one frame at 0, while a preview seeks (`-ss`) so its first frame is a little after 0 when no frame sits on the seek point (23.976 or 29.97 fps; `thumbnailSeconds` is exactly 1 s): overlay then passed the background through and the person was gone, though the key and the 85 % guard were right (the guard has no overlay in its graph, so it cannot see this). `keying-greens.test.ts` seeks with the real thumbnail time and off boundary offsets on a 23.976 fps clip and a single image background, and checks the render path too. Never lower these floors without running `tests/keying-check.ts` and the table in `src/lib/keying-greens.test.ts`.
- `background-preview` (spec 0008, pure): the cache identity (`cutVersion`: SHA-256 of `v{PREVIEW_STILL_VERSION}|` and the sorted applied cut ranges, 16 hex; bump `PREVIEW_STILL_VERSION` whenever a keying change makes the same take, background and cuts give a different still, so cached previews miss and are made again, as S3S-T10 and S3S-T12 did: now 3), `PREVIEW_LIMITS` (the job's 180 s and 2 attempts, the one place: the `preview-background` task reads them too) and `PREVIEW_STALE_MS` derived from it (every attempt plus a 2 minute queue margin: 8 minutes; a shorter limit reset a row whose job was still running and started a duplicate run). Waiting behind another preview of the same take is covered only by the margin, `previewKey`, the 1280 wide size and the keyed or plain ffmpeg graph for a still (it reuses `compositeFilters`). `detectInFrame` in `keying.ts` is the one frame detection (10 of 16 patches). The final gate (S3S-T12, `PREVIEW_GATE`, `centreDifferenceShare`, `isOnlyBackground`): after a keyed still is encoded, the job reads it and the background at 192 wide (the background through the preview graph's own chain at 1280 first, then down, as the still was made: a one step read of a detailed colour image differed in most of the centre third) and counts the pixels of the centre third that differ by more than 30 of 255 in a channel; under 2 % means no person is in the still (a real one differs in tens of percent, an erased one in 0.0 %), so the preview shows the plain frame with `no_green_screen`. `BACKGROUND_CHANGE.perHour` (10 background changes per creator per hour) lives in `background-rules.ts`; `PROCESS_TAKE_LIMITS.perCreatorConcurrency`, `CLEANUP.queuedStaleMs` and `queuedBackstopMs` in `cleanup-rules.ts`.
- `waveform` (spec 0011, pure): `waveformFromSamples(samples, durationMs)` turns mono samples into `min(1000, ceil(durationMs/100))` loudness values, 0 to 100 (`100 × clamp((20·log10(rms)+60)/60, 0, 1)`, silence 0); `samplesFromPcm16` decodes the job's ffmpeg output. The ffmpeg side is `src/trigger/waveform.ts`; never log the values.
- `cut-review` and `cut-playback` (spec 0011, pure): the page's cut review state (`numberCuts`, the edits that differ from the take GET and `normalizeEdits`, `pendingItems` in AC-4 order, `changeBody` for `POST /changes`, `timelineWidth` = `max(container, 8 px per second)`, `blockRect` with the 12 px block and 24 by 44 px hit area) and the preview's frame skips and playhead mapping through `latestRender.removedRanges`. `change-messages` words the `/changes` refusals. Nothing here may import the DOM.
- `job-errors` (pure, HRF-T10): `JOB_ERROR_NAMES` and `hasJobErrorName`, the one place the job error names live (see `src/trigger/AGENTS.md`).
- `deadline` (pure): `runWithDeadline` aborts a job attempt 90 s before `maxDuration`, waits for the work to clean up, then throws `DeadlineExceeded` (mapped to `timeout`); see `src/trigger/AGENTS.md`.
- `background-start` (pure, S3S-T13; the take page no longer calls it since S4C-T03, it goes with `PUT /api/takes/[id]/background` when that route is removed): `backgroundStartMessage(status, data)` (the server message, else a fixed wording per status, so a refused background change is never silent), `refusalMeansStalePage` and `LINK_REFRESH_MS` (see `src/components/takes/AGENTS.md`).
- API shapes and wording: `take-api` (zod), `take-display`, `take-messages`, `upload-client`.
- Email (spec 0006): `email/send` (Resend, the only network edge), `email/templates` (pure), `email-links` (signed turn off links, Web Crypto). Used by the Worker and by the `notify-take` job.
- Transcript read time (spec 0007): `transcript-timeline` (stored word times to the trimmed video with the render's own `alignToFrames(keepRanges(...))`, caption cues, SRT, VTT, plain text; all pure) and `transcript-download` (formats, file body, `Content-Disposition` with a safe name). The CC track, the SRT and the text all come from the same cues and paragraphs; never build captions anywhere else.
- Backgrounds (spec 0008): `background-rules` (limits, `backgroundKeys`, the failure codes with their friendly messages, `checkImageFacts`, `displaySize`, `rotationFilter`, `isAnimatedWebp`; pure, shared by the routes, the task and the picker) and `background-api` (zod shapes of the list).
- Config: `env` (zod parsers), `worker-deploy-config`, `server-source-maps`, `sentry-*` (options, scrubbing, check guard, debug ID).
- Small helpers: `result`, `utils`, `usage-hash`, `fonts`, `auth-client`.

## Conventions and gotchas

- Most modules are pure or take their I/O as a parameter (`upload-client` does), and tests rely on that. The ones that do I/O are `env` (reads `process.env`), `r2` (network), `email/send` (network, Resend), `r2-file-upload` (Node files), `trigger-runs` (Trigger.dev SDK), `fonts` (`next/font`, web only) and `auth-client` (browser, `"use client"`). Keep new modules pure unless they belong in that list.
- Imports (ESLint, `eslint.config.mjs`): `src/lib` may not import `@/app`, `@/server`, `@/trigger` or `@opennextjs/cloudflare`. It may import `next`, but jobs may not, so anything a job uses must stay free of `next`.
- `transcript-rules` (spec 0007): the stored word shape (`TranscriptWord`, times on the original upload) and `FILLER_WORDS`/`isFillerWord`, plus `TranscriptEdit` (an AI word fix: `index`, `old`, `new`, `reason`, `undone`) and `editedWords(words, edits)` (spec 0012: shows each live fix whose `old` still matches the word; counts, order and times never change). `transcript.text` and `transcript.words` are never rewritten; `toTrimmedTranscript` applies `editedWords` first, so the GET, SRT, VTT and text all show the same fixes, and `TrimmedWord.index` is the word's index in `transcript.words` (what the undo route takes).
- `ai-edit` (spec 0012 task 2, pure): the `AI_EDIT` config, `buildAiRequest` (its `estimatedInputTokens` is `estimateInputTokens`: 2 characters per token plus a fixed 640, fitted to two real counts, so the 60 000 guard means about 60 000 real tokens), the answer schema and `validateAiEdit` (item level drops, answer level `invalid`, word cuts clipped around kept pauses). `processing.ts` `SKIP_REASONS` also holds `ai_unavailable`; `aiEditEnvSchema` / `parseAiEditEnv` (`ANTHROPIC_API_KEY`) is parsed only by the job. Never import `@anthropic-ai/sdk` outside `src/trigger` (ESLint enforces it).
- `deepgram` (spec 0007): pure. The request options (`deepgramUrl`, always with `mip_opt_out=true`) and `parseDeepgramResponse` (zod, `en*` is English, words, fillers, paragraph starts, `not_english` and `no_speech` results). The fetch lives in `src/trigger/transcribe-take.ts`. `transcriptEnvSchema` (`DEEPGRAM_API_KEY`) is parsed only by that task. `processing.ts` also holds `SKIP_REASONS` (`not_english`, `no_speech`, `original_gone`, `no_green_screen`: stored in `job_step.failure_code` only on a skipped step; a failed step carries a failure code, never both), `jobKindSendsEmail` (only `initial` emails; `rerender`, `background` and `transcribe` never do). Job kinds: `initial`, `rerender` (a re render started by `startJob`), `background` (a background change; `isBackgroundKind(kind)` is the only test, a `rerender` never counts as one) and `transcribe`; `jobFamily(kind)` has no default branch, so a new kind fails the type check until it is placed and `LIVE_SLICE = 3`; `stepsFor(kind, { hasBackground })` creates the `background` step only for a job with a background. `transcript` is a step of the `transcribe` kind, not of `initial`. `TRANSCRIBE_TAKE_LIMITS` (3 attempts, 15 minutes) sets that kind's stale cutoff (50 minutes; video jobs 85).
- Registries are add only. Failure codes are an open set with no database check (see [src/trigger](../trigger/AGENTS.md)). The status, job, step and render lists in `processing.ts` build Postgres enums and checks, so never rename or remove a value. `LIVE_SLICE` keeps steps from later slices out until it is raised, and a step missing from `STEP_WEIGHTS` counts as 0 in the progress bar. `transcript` belongs to `initial` and `rerender` (spec 0012) and is non fatal: a `failed` or `skipped` transcript step shows as "Skipped" in the steps list (`stepStatusText`).
- Units: `maxDurationSeconds` is in seconds; every other timing in `cleanup-rules.ts` is in milliseconds. `TRIM.minSilenceMs` is milliseconds and is divided by 1000 for ffmpeg. When the frame rate is unknown, `alignToFrames` and `outputFps` both assume 30.
- `usage-rules` (spec 0014, pure): the monthly allowance. `FREE_MONTHLY_SECONDS_DEFAULT` (3600) is only the fallback for the `free_monthly_seconds` setting; `parseUsageSettings` turns bad or missing values into 3600 and limit off. `monthlyAllowanceSeconds(settings, account)` is the one place an allowance is decided (billing adds plans and the founding member override there later). `fitsInAllowance`, `remainingSeconds`, `resetsOn(now)` (first of the next UTC month), `usageSummary`, `usageDisplay` (minutes left rounded down, minutes used = allowance minus left), `usageNotice` (`low` from 80% used, `USAGE_NOTICE_FROM`) and `limitExceededMessage` (reset date and video expiry date come from the numbers; says upload again when the video expires before the reset). `limit_exceeded` in `failure-codes.ts` is not refundable and never charges.
- Usage hash: usage is stored under an HMAC of the canonical email (`usage-hash.ts`): lowercased, `+tag` removed, and for Gmail the dots removed and `googlemail.com` written as `gmail.com`. `USAGE_HASH_SECRET` (at least 32 characters) has its own schema in `env.ts` and is parsed only where the hash is computed. `USAGE_HASH_VERSION` is stored beside each row. Changing the canonical rules or the version changes every hash, so old usage would stop matching. Never log the secret or the email.
- `legal-facts` (spec 0015, pure): what the Privacy and Terms pages state. `PROCESSORS` (each service with env names and packages), `COLLECTED`, `COOKIES`, `LEGAL_NUMBERS` (read from `take-rules`), `LEGAL_VERSION` (ISO dates, bumped by hand), `LEGAL_ENTITY` and `REVIEW` (all `null` until Toyin and a lawyer supply them), the placeholder decisions (`MINIMUM_AGE`, `ACCOUNT_DELETE_SELF_SERVE`, …, one line each) and `draftReasons` (when the Draft banner must show). `legal-facts.test.ts` fails when an env name or a runtime dependency is in neither the registry nor its allowlist, when `mip_opt_out` is not true, when Sentry personal data turns on, or when a cookie is set besides the session one. A change that adds a service, cookie, stored field or retention change must update this file, the copy and the date. The page text hash test arrives with the pages.
- Legal change checklist (spec 0015 AC-10): a change that adds or removes a runtime dependency (a service goes in `PROCESSORS`, a plain tool in `NON_DATA_PACKAGES`), adds an env secret (`PROCESSORS.envNames` or `NON_PROCESSOR_ENV`), sets a cookie, stores a new personal field (`COLLECTED`), changes a retention number (`take-rules`, `storage-lifecycle`), changes what Deepgram, Anthropic, Resend or Sentry receive, adds an analytics event or adds a payment step must update `legal-facts.ts`, the page copy and the `LEGAL_VERSION` date in the same PR. `pnpm legal:drift` lists watched files (`LEGAL_WATCHED_PATHS`) changed without `legal-facts.ts`; /sync runs it and reports any hit under its heads up. `pnpm test:legal-launch` is the launch gate (not in `pnpm test`): it fails until `LEGAL_ENTITY` and `REVIEW` are filled and match the live versions, text hashes and allowance (read from `DATABASE_URL_DIRECT`, so point it at the launch database; a remote one needs `MIGRATE_TARGET=prod`).
- `legal-links.ts` (spec 0015 AC-2): the `/privacy` and `/terms` routes and link labels. The footer, the sign in notice, the upload note and the user menu all take their links from it; `src/components/legal/legal-notice.tsx` holds the notice and the upload note (links only, no checkbox, nothing stored while `AGREEMENT` is `notice`).
- `legal-text-hashes` (spec 0015 AC-7, AC-9): one `{ date, hash }` line per version of each page's copy. The copy components in `src/components/legal/` are the single source; `legal-copy.test.ts` hashes them (`legalCopyHash`, every allowance wording and entity field as a token) and fails when the hash is not recorded under the current `LEGAL_VERSION` date, or a date is recorded twice. To change the copy: edit it, bump the date in `LEGAL_VERSION`, run the test to see the new hash, add a new line (never edit an old one). The pages use the recorded hash for the Draft banner; `pnpm test:legal-launch` hashes the live components instead.
- `emailEnvSchema` (app URL, Resend key, sender, link secret) is parsed only where email is sent or a link is signed; `BETTER_AUTH_URL` must also be set in Trigger.dev, or `notify-take` stops at once with a names only error.
- Durations shown to people (take length, player time, "Removed m:ss of pauses", the same number in emails) all go through `formatClock` in `take-display.ts`, which floors to whole seconds (2501 ms is `0:02`). Never write a second formatter; emails import this one.
- `env.ts` error messages name the variables and never show values.
- `take-media.ts` keeps its own copy of the media failure codes next to the one in `failure-codes.ts`. They are the same today; change both, or remove the copy.
- One exported function per rule, never a hand written copy: whether a take's video has expired is `isVideoExpired(videoExpiresAt, now)` (`video-expiry.ts`: null is not expired, equal to now is expired; `isExpired` in `take-media.ts` adds the `expired` status) and a media failure is `isMediaFailure` (`failure-codes.ts`). A test (`video-expiry.test.ts`) fails on a hand written expiry comparison or a second copy of the media codes. The sweep's SQL (`lte(take.videoExpiresAt, now)`) says the same thing in the database.
