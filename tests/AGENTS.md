# Tests (tests/ and how to run each kind)

- Unit: `pnpm test` (Vitest, only `src/**/*.test.ts`). Database tests need `pnpm db:up`.
- Browser: `pnpm build:worker`, then `pnpm test:e2e`. It runs against a built Worker (`opennextjs-cloudflare preview` on 127.0.0.1:8787), not `next dev`, and nothing builds the Worker for you. Locally a stale preview server is reused (`reuseExistingServer`), so stop old ones. It needs Postgres: `tests/support/session.ts` seeds users and sessions and forges Better Auth's signed cookie, so the Worker must be built with the same `BETTER_AUTH_SECRET`, and non local hosts are refused. CI writes a placeholder `.env` before the build because OpenNext bundles it.
- The design specs split by mode: `design.spec.ts` and `design-components.spec.ts` skip when `E2E_PRODUCTION=1`, and the production check is a separate run.
- Pipeline: `pnpm test:pipeline` is the API level end to end check against the real R2 and Trigger.dev dev environments. It is a pre release check, not PR CI, and needs R2 and Trigger.dev keys (`harness.ts` lists them), Docker Postgres, and ffmpeg 7 with libx264 and libx265. It starts `next dev` and `trigger dev` as child processes; the root `AGENTS.md` says what to do when a failed run leaves them behind. On a 3 GB sandbox run nothing else beside it (no browser, no `NODE_OPTIONS` set to the full RAM): when the app is killed for memory the harness only prints `fetch failed` on every check. A clean run is 104 checks (the transcript checks of spec 0007 need `DEEPGRAM_API_KEY` in the shell and call real Deepgram with tiny synthetic clips, a few cents; they use their own creator because of the 10 uploads per hour limit). `next dev` opens a database client per request and never closes it, so the harness closes connections idle for 30 s itself and stops its servers on exit, failure or Ctrl+C; a run that still dies with "too many clients" or `trigger dev` "Worker timed out" needs the leftovers killed and `docker compose restart postgres`.
- Keying check (spec 0008): `tests/keying-check.ts` runs the synthetic green screen and no green screen clips through the real `process-take` (needs `trigger dev` with the proxy env file, `pnpm db:seed` and a local database), prints the steps, the render row and the output facts, and counts green pixels in a band around the subject (there must be none). Set `OUT_DIR` to keep a frame of every output.
- Manual checks: `tests/probe-check.ts` and `tests/process-check.ts`, run as `DATABASE_URL_DIRECT=postgres://postgres:postgres@localhost:5432/take_studio pnpm tsx tests/probe-check.ts`.
- Fixtures: `tests/fixtures/media/` is committed. Regenerate with `bash tests/fixtures/make-media.sh`, `bash tests/fixtures/make-pause-media.sh` and, for the transcript checks, `bash tests/fixtures/make-speech-media.sh` (synthetic Deepgram voices, needs `DEEPGRAM_API_KEY`) and `bash tests/fixtures/make-keying-media.sh` (synthetic green screen and no green screen clips: a person shape on #00B140 or on a wall, one still frame looped, so the files are 40 to 180 KB); the pause fixtures depend on exact tone and flash timings written in the script comments.
- In CI Playwright retries once and `forbidOnly` is on.
- CI e2e runs in the official Playwright container image (`PLAYWRIGHT_IMAGE` in `.github/workflows/ci.yml`, `docker run --network host`), not on the runner, so no `apt-get` runs at run time (`ubuntu-latest` moved to a newer Ubuntu whose apt mirrors were unreachable and blocked every PR, so every workflow now pins `runs-on: ubuntu-24.04`; a test fails if `ubuntu-latest` returns). The tag must equal the exact `@playwright/test` version in `package.json`: bump both together, `src/ci-config.test.ts` fails the build on drift or if `apt`, `install-deps` or `--with-deps` return. Only the e2e step is in the container (the build, Postgres service and `.env` stay on the runner), and the runner's own Node (from `.nvmrc`) and `pnpm` are mounted read only into the container and put first on `PATH`: the image ships a newer Node and no `pnpm`, and the tests and the preview must run on Node 22 like everything else.
- Keyboard tests on a Radix menu must wait for a readiness signal that is set after the page's effects have run before pressing keys: Radix only learns a menu was opened from the keyboard through a document listener added in an effect, and an early Enter leaves focus on the menu instead of the first item. On the `/design` gallery that signal is `[data-overlays-ready='true']`, set by `OverlayDemos`; a menu on any other page needs its own signal. Never fix this with a sleep or a retry.
